# 搭拍子商业审视与近期优化

审视日期：2026-09-05。依据为当前工程、API 契约与发布清单；未取得真实运营、收入或生产后台数据。以下市场定位、获客和收费方式均是待验证假设，不代表已建立合作或已证明盈利。

## 商业判断

搭拍子的清晰价值是：让已经有打球习惯、临时缺球友的人，在常去球馆找到时间和练习预期合适的搭子，加入后完成必要沟通。

相对微信群，值得验证的优势是可查找的日期/球馆、实时名额、统一安排和取消处理。用户不会只因页面更好看而持续迁移。找到固定搭子后，他们还可能回到微信直接联系；持续使用的理由应来自补位、安排与复约的便利。

目前工程覆盖发布、加入、申请、候补、成员沟通和取消；尚未验证真实成局、到场和付费意愿。球台状态由发起人填写，平台没有场馆实时库存或订台交易能力。Playtomic 的公开球局与场馆排期相连，不能仅凭相似 UI 视为同样的商业模式。

## 九个模块

| 模块 | 当前依据 | 下一步验证 |
| --- | --- | --- |
| 客户细分 | 球友约局和教练预约已有入口；发起人与参与者是同一用户群中的不同角色 | 先集中少数邻近球馆的经常打球人群；教练作为受控试点 |
| 价值主张 | 球馆、时间、人数、球龄/技术、加入后沟通 | 用户是否更快找到合适的人，并实际打成一场 |
| 渠道通路 | 微信好友、朋友圈公开页分享已实现 | 哪些场馆前台、现有球友群和主理人可以持续带来真实参与 |
| 客户关系 | 自助操作、申请审批、聊天、取消、举报/屏蔽 | 到场确认、安排提醒、复约能否带来再次使用；保持低社交负担 |
| 收入来源 | 平台不代收球局或教练费用，工程未接入收费 | 与愿意合作的场馆/教练测试可归因预约服务费；暂不假设收费率 |
| 关键资源 | 小程序、云 API、候选场馆目录 | 可持续发局的主理人、可确认的球台与当地活跃用户密度 |
| 关键活动 | 工程已定义核验、审核与异常处置流程 | 场馆回访、真实组局、处理取消与争议；记录每场运营时间 |
| 关键伙伴 | 仓库有待核验候选球馆，不等于已签约伙伴 | 确认合作方、获客入口、订台方式、时段与费用更新责任 |
| 成本结构 | 云资源、媒体审核、安全运维均有需求 | 统计获客、核验、客服和组织活动的人力成本，验证每场成本是否下降 |

## 本轮产品优化范围

1. 无结果时提供主动放宽筛选的入口：先放宽日期和球龄，保留地区；用户再次选择时再看全杭州。教练搜索保持独立。
2. 订台状态明确为发起人提供的信息；申请、候补和已加入使用不同说明，避免把加入成功表达为订台成功。
3. 历史球局可生成“再约一场”的未提交草稿；重新选择/确认时间和订台状态，保护原有草稿，不自动发布或邀请旧成员。
4. 首页缓存跨天返回时刷新日期；紧凑布局允许日期和时段换行，减少窄屏挤压。
5. 首页分页结果可继续加载，数量标识不冒充总量；筛选变化后不让旧分页混入新的结果。
6. 加入成功后使旧详情请求失效；刷新失败保留刚确认的状态，避免重复操作。发起人不显示屏蔽自己的入口。

## 试运营建议

建议先选择 3–5 家邻近球馆作为试验范围；该数量是控制运营工作量的假设，不是市场结论。优先找到愿意持续发局的球友，并确认实际可订时段。热门时段可能利于球友成局，但场馆更需要非高峰增量，这两种需求应分别验证。

- 前两周：核验场馆、确定主理人、跑通真实账号与订台流程；访谈现有球友如何约局、最常在哪一步失败。
- 接下来四周：在固定时段组织规模可控的真实球局；记录流量来源、加入耗时、取消原因、到场情况和人工协调分钟数。
- 有重复使用后：测试复约对留存的作用；再与一家具备合作意愿的供给方验证付费方案。

不应把候选球馆当成合作场馆，也不应把公开页面浏览量当成有效预约。当前尚未查看生产后台，生产供给是否已由管理员补齐需要另行核实。

## 衡量是否值得扩大

核心指标建议是“每周经参与者确认实际到场的球局数”。当前没有到场确认数据，需要先建立轻量记录，不能以预约时间已过替代真实到场。

- 成局率：在预先约定的截止时间前，达到发起人所需人数的有效球局占比；不要混同“至少两人”与“全部满员”。
- 到场率：有效确认参与人次中实际到场的人次比例；退出、取消与无故爽约分别记录。
- 复约率：首次实际到场用户中，在后续 14 天再次到场的比例；排除观察窗口尚未结束的用户。
- 单场服务成本：可归属的运营、客服、补贴和云资源成本，除以真实完成的球局数。
- 收费验证：合作方认可多少由平台带来的有效预约、愿意支付什么费用、收入能否覆盖增量服务成本。

达到哪些比例才扩张，应结合第一批真实数据、用户体验和可承受运营投入设定；当前不虚构行业基准。到场确认应保持低负担，争议先人工处理，不急于建立公开信用分或惩罚榜。

本轮客户端体验优化不等于正式上线。当前自动发布检查仍要求填写隔离的测试和生产云环境 ID；其余部署、真实供给与真机回归按现有 RELEASE_CHECKLIST.md 验收。技术测试通过也不代表市场需求、成局率或收费方式已经得到验证。
